## 第 1 页：项目名称与开场（约 40 秒）

各位老师、各位同事，大家好。今天汇报的项目是“端侧大模型低比特量化与 MONET 结构化推理优化”。

这个项目关注的问题非常具体：大模型放到手机等端侧设备后，瓶颈往往不只是算力，更是内存容量、LPDDR 带宽、片上缓存和功耗。尤其在自回归解码阶段，设备需要不断搬运模型权重，计算单元可能没有被充分利用，实际速度更多受制于访存。

因此，我们没有把目标局限在“再降低一点量化位宽”，而是尝试同时改变权重表示、执行数据流和端侧运行方式，让模型结构更加适合移动端。

> 页面提示：标题、项目一句话目标，以及“模型表示—数据流—端侧执行”三个关键词。

## 第 2 页：项目要解决的核心问题（约 1 分钟）

端侧大模型常见的压缩路线包括量化、稀疏化和低秩分解，但三类方法都有工程上的限制。

第一，量化能够减少模型存储和访存，但位宽继续下降时，精度损失会快速增加。第二，非结构化稀疏在理论上减少了计算量，但不规则索引和访存很难在手机 CPU、GPU 或现有推理后端上转化为稳定加速。第三，以 SVD 为代表的低秩分解会把一次矩阵乘法拆成多次计算，rank 和中间张量形状不固定，还可能增加 DRAM 读写。

项目由此形成了一个判断：端侧优化不能只看参数量或理论 FLOPs，还要看 kernel 是否规则、中间结果是否需要落到内存，以及计算能否匹配手机端固定的执行粒度。

这也是项目从早期 SVD 和子空间分解探索，逐步转向 Monarch 结构化矩阵的根本原因。

> 页面提示：可参考[方案思路阐述](../docs/方案思路阐述.md)第 1、4、5 节，制作量化、稀疏、SVD、Monarch 的简要对比。

## 第 3 页：技术路线的演进（约 1 分钟）

项目早期面向 MoE 和多模态模型，探索了 CESD、GLAS 和 NGES 等方法：通过跨专家、跨层子空间分解降低冗余，通过全局损失对齐评估重要性，再利用零空间约束抑制专家偏移。之后，方案又从单一聚合推进到 layer-wise 和 block-wise 聚合。

这些探索形成了算法积累，但在手机端落地时，SVD 路线暴露出 rank 不稳定、kernel 不友好和中间访存较大的问题。也就是说，算法上可以压缩，不代表端侧真正跑得快。

因此，后续路线转向 Monarch。它的关键优势不是简单地“矩阵更小”，而是把大矩阵拆成固定大小的块对角计算和固定置换，使执行形状更加规则，更容易进行缓存优化、并行调度和后端实现。

> 页面提示：建议使用“早期子空间分解 → 手机部署反馈 → SVD 不适配 → Monarch”时间线。

## 第 4 页：MONET/Monarch 的核心思路（约 1 分 30 秒）

对于一个方阵线性层，Monarch 使用两组块对角因子和置换来近似原始稠密矩阵。以 LLaMA-2-7B 中常见的 4096×4096 attention projection 为例，可以取 64 的块大小，把矩阵划分为 64 个规则块。

从当前拟合脚本和 I02 数值参考实现可以确认，行向量计算顺序是：先执行 R 的块对角乘法，再按照 permutation 做 gather，最后执行 L 的块对角乘法。

这种表示带来三个工程上的可能收益：

第一，块尺寸和执行路径固定，方便针对 CPU、ARM NEON 或其他后端实现规则 kernel。第二，可以把 permutation 融入数据布局或后续块访问，减少显式中间张量。第三，可以进一步在离线阶段评估不同块的重要性，形成固定的块级保留策略。

需要特别说明的是，前两组块因子与置换的数值语义已经有 NumPy reference 和单元测试；但当前仓库中的 `llama.cpp` forward graph 还没有实际消费这些 L/R/perm tensor。因此，这一页讲的是“已经形成并部分验证的技术路线”，不是宣称完整 runtime 已经闭环。

> 页面提示：可参考[中文项目说明手册](../docs/中文项目说明手册.md)第 0、4、5、11.2 节。建议配一张“R 块计算—置换—L 块计算”的简图。

## 第 5 页：完整工程链路（约 1 分 30 秒）

项目手册把完整工程流程划分为五个阶段。

第一阶段是在 PyTorch 侧采集 WikiText-2 激活，对 attention 中的 q、k、v、o 方阵投影拟合 Monarch 参数，并保存每层的 L、R、perm 和误差指标。这里采用的是激活感知拟合，也就是让 Monarch 层在真实输入激活上的输出接近原始稠密层，而不只是直接拟合权重矩阵。

第二阶段是把 Monarch 参数重新展开为 dense weight，生成 Monarch-dense HF 模型。这一步本身不产生压缩收益，作用是先验证拟合质量，避免把算法误差和后续 runtime 实现问题混在一起。

第三阶段是生成 Monarch-extra GGUF。这个调试格式同时保留原始 dense 权重和 L/R/perm extra tensor，便于逐步验证 converter、reader、loader 和 graph。

第四阶段是在 `llama.cpp` 中完成 tensor 认领、graph 接入、自定义算子和 CPU/ARM 等后端实现。

第五阶段才是生成真正减少被替换 dense 权重的 Monarch-only 模型，并在 Windows、WSL 和 Android 上完成正确性和性能测试。

这一分阶段设计的价值，是把算法拟合、模型格式、加载、计算图和端侧后端分别验证，出现问题时能够明确定位。

> 页面提示：直接采用手册第 1 节的五阶段流程，标注“已确认”“部分实现”“规划/待验证”三种状态。

## 第 6 页：当前仓库可以确认的实现（约 1 分 30 秒）

结合当前代码审计，可以确认的实现主要有四部分。

第一，拟合脚本已经实现方阵 attention projection 的激活采集、逐层拟合，以及 L/R/perm 和误差汇总保存。

第二，GGUF 转换脚本提供 `--monarch-dir` 和 `--monarch-dtype`，能够把 Monarch 参数映射到 `blk.i.attn_q`、`attn_k`、`attn_v` 和 `attn_output` 对应的 extra tensor 命名空间。

第三，I01 增加了转换前输入校验。它会检查参数包字段、层名、shape、dtype、有限值、permutation 完整性和重复映射，并在非法数据进入 GGUF writer 之前快速失败。

第四，修改版 `llama.cpp` 中已经存在 Monarch 权重结构、q/k/v/o 四组字段、可选 tensor 创建与 loader 认领框架；I02 又补充了独立的 NumPy forward 和稠密矩阵对照，为后续 C++/GGML graph 实现固定了数值基线。

同时也要明确当前边界：仓库中还没有可确认的 `GGML_OP_MONARCH_LINEAR`、专用 CPU/ARM kernel或 forward graph 调用。因此，现阶段不能把“参数已进入 GGUF 和 loader”直接等同于“推理已经使用 Monarch 计算”。

> 页面提示：建议展示“拟合脚本—converter—loader—NumPy reference”四个已确认模块，并把 graph/op/backend 用虚线表示。

## 第 7 页：本轮代码质量与验证闭环（约 1 分钟）

为了让后续实现有可复核基础，目前已经完成两轮小批次验证。

I01 针对参数包校验增加了 12 个单元测试，覆盖合法层名、兼容字段、L/R shape 和 dtype、NaN/Inf，以及 permutation 重复、越界等失败路径。

I02 针对 forward 数值语义增加了 6 个测试。测试不仅运行直接分块算法，还独立构造完整的块对角矩阵和 permutation matrix，对两条不共享 forward 逻辑的路径进行比较；同时检查单块退化、gather 方向、多维输入和错误输入。

截至当前，完整 MONET Python 测试集是 18 项，全部在 Windows、Python 3.12.13、NumPy 2.3.5 环境通过，相关 Python 文件也通过语法编译检查。

这些测试证明的是转换前校验和方阵数值契约，不替代真实模型转换、C++ graph、端侧设备或最终性能验收。

> 页面提示：引用[I01 验证记录](verification/iteration-I01.md)和[I02 验证记录](verification/iteration-I02.md)，突出“18/18”及测试覆盖范围。

## 第 8 页：阶段性实验与演示证据（约 1 分 30 秒）

现有材料中有三类性能证据，需要分开解读。

## 第 10 页：验收判断与当前限制（约 1 分 20 秒）

基于现有仓库，我们可以比较确定地说：项目已经形成了清晰的问题定义、算法演进路线、Monarch 拟合与模型格式原型、部分 loader 适配、数值参考、自动化测试，以及论文和专利交底成果，能够支撑技术阶段性成果的审核。

但当前还不能直接作出“全部合同指标达标”或“完整 runtime 已通过验收”的结论。主要缺口包括：

第一，缺少可公开复现的真实 Monarch 参数包、HF 权重和生成后 GGUF，尚未闭环 `.pt → GGUF → reader → loader`。第二，`llama.cpp` graph、自定义 GGML op 和目标 backend 仍需实现并与 NumPy reference 对齐。第三，Android 构建、正确性、吞吐、内存、功耗和温升需要在固定设备上重新测试。第四，任务书指标、成本、人力投入、业务应用证明和正式验收意见属于外部管理材料，不能由代码替代。

因此，本项目当前更准确的结论是：技术方案和阶段性成果已经形成，核心工程链路仍需继续闭环，正式验收结论应由项目负责人和验收组在补齐外部证据后给出。

## 第 11 页：后续工作（约 50 秒）

后续工作建议按照证据链顺序推进，而不是直接进入大规模后端优化。

第一，以当前 NumPy reference 为 oracle，建立固定小矩阵的 C++/GGML graph 数值测试，确保 graph 真正消费 L/R/perm，并验证 dense 回退不回归。

第二，补充最小真实 `.pt` 参数包和可复现 HF 模型，完成 converter、GGUF reader 和 loader 的端到端闭环。

第三，在主机端数值和加载均稳定后，再实现自定义 op、CPU reference 和 ARM 后端优化，最后生成 Monarch-only GGUF，并在固定 Android 设备上统一复测正确性、吞吐、内存、功耗和温升。

这样可以把每一步都绑定到固定输入、命令、代码提交和原始日志，逐步把研究结果转换为可验收的工程证据。

## 第 12 页：总结（约 40 秒）

最后总结一下。MONET 项目的核心价值，不是单纯追求更低的理论计算量，而是从端侧真实瓶颈出发，把模型表示、访存数据流和硬件执行粒度放在同一个优化框架中考虑。

项目已经完成从早期子空间和 SVD 路线到 Monarch 结构化路线的技术演进，形成了算法、转换、加载、测试、论文和技术交底等阶段性成果；当前也已经通过代码审计和持续测试，更清楚地划定了“已经验证的内容”和“仍需闭环的 runtime 与端侧验收”。

后续工作的重点，是以可复现的数值基线和真实模型证据为核心，补齐 graph、backend 和 Android 验收链路。

## 评审问答准备

### 1. MONET 和普通低比特量化是什么关系？

MONET 不是简单把所有权重直接降到 INT4 或 INT8，而是用规则的块对角因子和置换表示部分线性层，并可与现有量化 kernel 或混合精度策略组合。当前仓库优先处理 attention 中的 q/k/v/o 方阵，矩形 MLP 尚未纳入当前实现范围。

### 2. 为什么不继续使用 SVD？

SVD 的理论 FLOPs 可能更低，但 rank 不固定、矩阵形状不规则，而且会引入多阶段计算和中间张量读写。在移动端带宽受限场景中，这些成本可能抵消理论收益。Monarch 使用固定块尺寸和固定置换，更适合提前规划 kernel、缓存与并行路径。

### 3. 当前代码是否已经真正使用 Monarch 推理？

当前代码能够确认拟合、GGUF extra tensor 转换、输入校验、模型字段、loader 认领框架和 NumPy 数值 reference。当前 `llama.cpp` graph 仍使用 dense projection，仓库中尚未确认完整自定义 op 和后端 kernel，因此不能表述为完整 runtime 已闭环。

### 4. 18 个测试证明了什么？

其中 12 个证明参数包和层名映射能对合法、非法输入做出明确判断；6 个证明方阵 Monarch 的 `R → gather(perm) → L` 数值语义与独立稠密物化一致。它们不证明真实 GGUF、C++ graph、Android 设备或论文性能已经复现。

### 5. 为什么论文数据和截图数据不完全一致？

它们可能来自不同设备、模型、后端、优化版本和统计方法。现有仓库不足以统一这些条件，因此讲稿把截图与论文结果分别列示，不进行混合比较。正式验收需要固定环境并保留原始日志。

### 6. 项目是否已经结项？

从技术材料角度，已经形成可供审核的阶段性成果包；但是否达到任务书全部指标、是否正式通过验收，需要任务书、指标对照、外部测试、成本及验收会议记录支持，不能只依据当前代码和论文材料作出结论。
