1. 项目产出\(是否达标、是否通过、是否结项，可结合**验收报告**进行关键陈述）

    1. **项目背景及拟解决问题**

       【综合归纳】移动端 SoC 受 LPDDR 带宽、片上缓存容量、功耗和执行后端限制，自回归解码通常呈现低算术强度，推理性能更多受权重搬运与中间数据读写约束。传统量化可以降低位宽，但极低位宽可能造成明显精度损失；非结构化稀疏会引入不规则访存；SVD 等低秩方法可能增加中间张量和多阶段同步，理论 FLOPs 收益不一定转化为移动端实际时延收益。项目因此将目标从单纯“降低计算量”调整为“结构化权重表示、IO 感知数据流和硬件执行粒度协同优化”。详细论述见[方案思路阐述](../docs/方案思路阐述.md)第 1、4、5 节和[投稿论文](../docs/投稿论文.pdf)第 1—4 节。

    2. **总体目标与主要场景**

       【材料记载】项目目标是在 `llama.cpp` 中支持基于 Monarch 矩阵的结构化模型压缩方案，并完成 Windows/WSL/Android 手机端部署验证。主要场景包括手机本地对话、离线文本生成与理解、隐私敏感数据本地处理，以及可进一步扩展的车载、可穿戴、AIoT 和端云协同推理。参见[中文项目说明手册](../docs/中文项目说明手册.md)“项目目标”和[移动端推理优化技术交底书](../docs/技术交底书-一种基于块分解的面向移动端大模型推理优化方法.docx)第 2.1 节。

    3. **技术路线及实施演进**

       【材料记载】项目早期面向 Qwen3-VL/MoE 探索 CESD（跨专家/跨层子空间分解）、GLAS（全局损失对齐显著性）和 NGES（零空间引导的专家偏移抑制），并从单一聚合推进到 layer-wise、block-wise 聚合。材料报告该路线在 MMMU、BLINK、MVBench 等任务上进行了比较，但移动端落地时发现 SVD 路径存在 rank 不稳定、执行形状不规则和中间访存增加等问题。

       【综合归纳】后续路线转向结构更规则的 Monarch/语义块分解：将稠密线性变换近似表示为置换与两组块对角因子的组合，并进一步提出三层协同设计：

       - 架构感知的块分解：依据层形状、局部结构和目标硬件选择块尺寸；
       - 带宽感知的流式执行：将显式 permutation 融合到数据布局/散射写入中，减少中间张量物化与 DRAM 往返；
       - 成本感知的离线块裁剪：基于校准集估计块输出贡献，在精度约束下生成固定执行掩码。

       当前论文将该路线概括为 MONET（Semantic Block Decomposition），两份技术交底书分别覆盖“面向移动端的块分解与流式执行”和“跨层块级子空间聚合、GLAS 与低位残差表示”。三者存在技术承接关系，但不是完全相同的实现分支。

    4. **算法拟合与模型转换工具**

       【代码确认】[`scripts/fit_all_square_monarch_wikitext.py`](../scripts/fit_all_square_monarch_wikitext.py)实现了方阵线性层的 `MonarchLinear` 原型，执行 `blockdiag(R) → permutation → blockdiag(L)`，使用 WikiText-2 激活拟合稠密层输出。默认配置包括：块大小 64、校准样本 128、序列长度 128、每层最多 8192 个激活 token、1000 个拟合步，默认目标关键字为 `q_proj,k_proj,v_proj,o_proj`。脚本保存每层 `L/R/perm`、误差指标以及 CSV/JSON 汇总。

       【代码确认】[`llama.cpp-monarch/convert_hf_to_gguf_monarch.py`](../llama.cpp-monarch/convert_hf_to_gguf_monarch.py)增加了 `--monarch-dir` 和 `--monarch-dtype` 参数，可从 `.pt` 文件读取 `L/R/perm`，映射为 `blk.i.attn_*.monarch_l/r/perm` 并追加到 GGUF writer。Iteration I01 新增[`monarch_tensor_validation.py`](../llama.cpp-monarch/monarch_tensor_validation.py)，在写入前检查安全加载、对象字段、支持层名、L/R 形状与有限值、permutation 完整性和重复 GGUF 映射；非法输入会在 writer 注册前失败。当前实现仍保留原始 dense tensor，属于便于调试的 “Monarch-extra GGUF” 路径；代码中未发现 `--monarch-only`。

    5. **`llama.cpp` 扩展与当前实现边界**

       【代码确认】[`src/llama-model.h`](../llama.cpp-monarch/src/llama-model.h)新增 `llama_monarch_weight` 结构及 attention Q/K/V/O 四组字段；[`src/models/llama.cpp`](../llama.cpp-monarch/src/models/llama.cpp)按块大小 64 创建可选的 `monarch_l/r/perm` tensor，并在三类 tensor 同时存在时标记启用；[`src/llama-model.cpp`](../llama.cpp-monarch/src/llama-model.cpp)使用 `done_getting_tensors(true)` 允许额外 tensor。

       【代码确认】在当前仓库中未检索到 `GGML_OP_MONARCH_LINEAR`、Monarch CPU/ARM kernel 或在 forward graph 中调用 Monarch tensor 的实现。因此，当前代码可确认到“参数拟合、GGUF 扩展、模型结构声明与 loader 认领/兼容”层面，不能仅凭现有源码认定“完整自定义算子、流式执行、块裁剪和端到端 Monarch runtime 均已提交到本仓库”。如完整实现位于其他分支、私有仓库或未提交目录，应在正式结项时补充。

    6. **测试与验证结果**

       【代码与测试确认—Iteration I01】[`test_monarch_tensor_validation.py`](../llama.cpp-monarch/tests/test_monarch_tensor_validation.py)新增 12 个单元测试，已在 Windows、Python 3.12.13、NumPy 2.3.5 环境全部通过；相关文件同时通过 Python 语法编译和 Git 差异格式检查。本轮环境未安装 PyTorch，也没有真实 Monarch `.pt` 参数包、HF 模型权重或 Android 设备，因此未执行真实 converter、GGUF reader、`llama.cpp` loader 或手机 benchmark。完整命令和边界见[验证记录](verification/iteration-I01.md)，代码提交为 [`c2769bc`](https://github.com/jlsbz/MONET-llama.cpp/commit/c2769bc)。

       【材料记载—截图可核验】[基线命令行截图](../docs/image-7.png)显示 Q4_K Medium 模型大小 3.80 GiB、pp128 为 7.87±0.27 t/s、tg128 为 5.63±0.20 t/s；[Monarch 命令行截图](../docs/image-8.png)显示模型大小 2.95 GiB、pp128 为 9.83±1.55 t/s、tg128 为 6.24±1.45 t/s。按截图读数，模型显示大小约下降 22.4%，pp128/tg128 分别约提升 24.9%/10.8%。截图未显示设备型号、运行次数、温控策略和完整命令，故应视为阶段性证据。

       【材料记载—截图可核验】Android App 截图显示 Monarch 模型 Prefill 10.66 t/s、Decode 7.16 t/s；基线模型 Prefill 8.70 t/s、Decode 6.62 t/s，分别约提升 22.5%和 8.2%。两张截图的生成内容不同，且缺少重复实验与统计信息，适合作为 Demo 证明，不宜直接作为最终验收指标。

       【材料记载—论文报告】投稿论文在两台 Android 设备的 `llama.cpp` GPU 后端上测试 LLaMA-2-7B、Qwen-2.5-7B 等模型，默认块大小 64、保留 75% 块、校准样本 256、序列长度 128、batch size 1。论文报告最高 2.42× Prefill、2.52× Decode，并给出 WikiText-2 PPL、MMLU、DRAM traffic、ALU/LSU 利用率及消融实验。以论文表 2 为例，LLaMA-2-7B-q4 的 Dense/MONET 分别为 PPL 7.45/7.72、MMLU 44.2/43.5；Qwen-2.5-7B-q4 分别为 PPL 7.10/7.38、MMLU 48.5/47.6，表现为有限但非零的质量下降。仓库未包含论文实验的原始日志、可执行复现脚本和模型文件，因此这些数字尚需验收级复核。

## 三、总结与反思

【综合归纳】项目的主要价值在于把研究重点从“理论 FLOPs 或参数量下降”推进到“模型表示—数据流—移动端硬件约束”协同设计，并用结构化块分解、流式执行和块级选择回应移动端内存带宽瓶颈。项目还形成了从早期 CESD/GLAS/NGES 与 SVD 路线，到 Monarch/语义块分解路线的清晰演进脉络。

当前最主要的结项风险不是缺少技术思路，而是“正式材料、论文陈述、阶段截图与当前公开代码”的实现边界没有完全统一：方案文档和论文描述了完整 runtime 与较高加速，而仓库中可直接定位的代码主要覆盖拟合、GGUF extra tensor 和 loader；不同材料中的内存流量、速度结果及测试环境也不完全一致。正式结项应以可复现证据为中心，统一版本、设备和指标口径。

## 过程回顾

| **序号** | **出现问题** | **原因分析** |
|---|---|---|
| 1 | 早期 SVD/低秩路线在移动端未稳定兑现理论计算收益 | LLM 各层低秩性不一致；多阶段矩阵乘法增加中间张量与 DRAM 读写；动态 rank 和不规则形状不利于移动端 kernel |
| 2 | 单一聚合策略在 MMMU、BLINK 等任务上出现较明显精度下降 | 不同层和 block 的敏感度、相似性和可压缩性不同，全局统一策略低估了关键层/块的重要性 |
| 3 | 文档所述完整运行时与当前仓库可定位代码之间存在缺口 | 研发版本可能分散在其他分支、私有目录或未提交产物；文档同时包含已完成内容、调试方案和后续规划，状态标记不完全一致 |
| 4 | 不同材料中的速度和内存流量数字难以直接横向比较 | 测试后端、设备、模型、量化位宽、序列长度和统计方式不同；仓库未附完整原始日志与统一复现入口 |

## 改进措施/经验

1. 建立“目标—实现—测试—证据”验收矩阵：每个任务书指标绑定代码版本、模型哈希、设备、命令、原始日志和审核人，避免只保留汇总数字或截图。
2. 统一研发状态标记：对“已实现、调试版、论文实现、计划实现”分别维护清单；若完整 runtime 位于其他分支，应在结项包中提供只读快照或明确链接。
3. 建立可复现端侧 benchmark：固定设备与系统版本、线程/频率/温控、量化格式、Prompt/序列长度、预热次数和重复次数，同时报告均值、方差、PPL/MMLU 与内存流量。
4. 将截图证据升级为正式测试报告：保留截图用于展示，同时附结构化 CSV/JSON、完整控制台日志和自动生成的对比表。
5. 对不同技术分支建立清晰关系：将早期 CESD/GLAS/NGES、跨层 SVD 专利路线和当前 MONET/Monarch 移动端路线分别说明，避免把研究探索、专利方案与最终工程实现混为一体。
6. 对外部成果采用严格状态词：论文仅在有录用通知时写“录用”，专利仅在有受理/授权文件时写“申请/授权”，产品应用仅在有业务证明时写“上线/应用”。
